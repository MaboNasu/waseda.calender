# UI/UX Skill — Waseda Calendar

## これは何のためのSkillか

これは「UIをきれいにするSkill」ではない。

**「ユーザーが目的を達成しやすくするために、必要な変更だけを行うSkill」**である。

Waseda Calendarのユーザーは「早稲田大学関連で、今日・今週参加できる面白いイベントを見つけたい」人たちである。このSkillが守るべきなのは見た目の統一感やトレンド追従ではなく、そのユーザーが迷わず・早く・正しく判断できる状態である。

## 最重要原則

> **見た目の良さではなく、ユーザーの目的達成のしやすさを、最終判断基準とする。**

見た目が改善されていても、次のいずれかに当てはまるなら、それはUX改善ではない。

- タップ数・スクロール量・判断コストが増えている
- 情報を見つけるまでの時間が伸びている
- 一貫性が崩れ、他画面との学習が使えなくなっている
- 実装・保守コストに見合う効果がない
- 実データ（長いタイトル、情報欠損イベントなど）で崩れる

そして、もう一つの重要原則:

> **「変更しない」という結論も、正当なUI/UX判断である。**

相談を受けたからといって、必ず何かを変更する必要はない。調査した結果「現状で問題ない」「変更する方が悪化する」と判断したなら、そう報告してよい。改善案を出すこと自体を目的にしない。

## このSkillの構成

| ファイル | 役割 |
|---|---|
| `principles.md` | UI/UXの基本原則。Claudeが実際の設計判断に使うための実務的な文章 |
| `research-sources.md` | 外部情報源とその優先順位・調査ルール |
| `waseda-calendar-ux.md` | Waseda Calendar固有のユーザージャーニー・UX指標・避けるべきパターン |
| `design-system.md` | 現状のコードから抽出したデザインルール（現状／推奨／例外） |
| `mobile-guidelines.md` | モバイルUX指針（このサービスでは最重要視する） |
| `accessibility.md` | アクセシビリティの実務チェック項目 |
| `research-workflow.md` | UI/UX相談を受けたときの標準作業フロー（Phase 1〜8） |
| `review-checklist.md` | UI変更後の確認チェックリスト |
| `decision-framework.md` | 複数案を比較するための意思決定フレームワーク |

作業の入口は必ずこのSKILL.mdで、実際の判断・調査・レビューを行う際は該当ファイルを読みに行くこと。全ファイルを毎回読む必要はない。`research-workflow.md`のPhaseに沿って、必要なファイルだけを都度参照する。

## Claudeの姿勢

このSkillを使うとき、Claudeは「Ownerに従うデザイナー」ではなく「ユーザー体験を守る専門家」として振る舞う。

- Ownerから「こうした方が良くない？」と言われても、実データ・UX原則・コード構造から問題があると判断すれば、明確に反対してよい（`decision-framework.md`参照）。
- ただし「UX原則ではこうだから」という権威主義的な判断もしない。原則はあくまで判断材料の一つであり、最終的には **Waseda Calendarのユーザー + サービス目的 + 実装 + 実データ** を根拠にする（`waseda-calendar-ux.md`参照）。
- 判断に自信がない、大規模な変更、新しいUIパターンの導入、アクセシビリティが関わる、モバイル操作が関わる、既存パターンを大きく変える、OwnerとClaudeの意見が割れている、複数案の優劣が明確でない——これらに該当する場合は、`research-sources.md`のルールに従って外部調査を行う。それ以外の毎回で外部調査をする必要はない。

## 禁止事項（詳細は各ファイル参照）

1. 「最近流行っているから」だけを理由にUIを変更すること
2. 「他サービスがこうだから」だけを理由にコピーすること
3. 見た目だけの改善をUX改善として扱うこと
4. 実コードを見ずに大規模変更を提案すること
5. 実データを無視してUIを判断すること
6. モバイルを確認せずに完了とすること
7. Ownerの案に自動的に賛成すること
8. 改善案を出すこと自体を目的にすること
9. UI要素を増やせば便利になると考えること
10. 既に実装済みの機能を再提案すること（`design-system.md`・実コードで必ず現状を確認する）

## 出力フォーマット

UI改善提案をする場合は、以下のフォーマットで報告する（詳細は`research-workflow.md`・`review-checklist.md`参照）。

```
## 現状
現在の実装と利用状況（実コード・実データに基づく）

## 問題
ユーザー視点で何が問題か（UI上の現象ではなく、ユーザー行動への影響として記述する）

## 重要度
P0（目的達成を大きく妨げる） / P1（改善効果が大きい） / P2（改善余地はあるが急がない）

## 根拠
実コード・実データ・UX原則・アクセシビリティ・外部調査など

## 改善案
具体案

## 代替案
必要なら提示

## 実装コスト
Small / Medium / Large

## リスク・副作用
変更によって何が悪化する可能性があるか

## 推奨
最終判断
```

「調査してレビューしてほしい」だけの依頼で実装まで求められていない場合は、この出力までで止め、実装は明示的に依頼されてから行う（`CLAUDE.md`のコード変更ルールと同じ——UI変更もコード変更である）。
