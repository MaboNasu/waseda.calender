# Waseda Calendar固有のUX

一般的なUI/UX理論と、このサービス固有のユーザー体験を接続するファイル。UI判断で最も参照頻度が高い。

## サービスの基本目的

Waseda Calendarは、早稲田大学および周辺のイベント情報を集約し、**「今日・今週、何か面白いイベントはないかな」というユーザーが、参加できるイベントを短時間で発見できるようにする**サービスである。

情報を自サービス内に囲い込むことが目的ではなく、以下の流れを支援する**イベントハブ**を目指す。

```
イベントを発見 → 興味を持つ → 参加可能か確認 → 公式情報を見る → 参加する
```

この目的意識は`LEGAL_GUARDRAILS.md`の基本思想（「公開されているイベントの事実情報を整理し、ユーザーを公式一次情報へ送客するハブ」）と完全に一致する。UIの判断でも、**「サイト内に留めること」ではなく「正しい情報に早くたどり着かせて外部（公式サイト・申込フォーム）へ送り出すこと」**を成功とみなす。

## 最重要ユーザージャーニー

```
流入 → イベントを発見 → 興味を持つ → 日時・場所・対象・料金等を確認
  → 自分が参加できるか判断 → 公式サイト／申込ページへ移動
```

UI/UX改善では、この各段階に存在する摩擦を減らす。どの段階の摩擦を減らそうとしているのかを常に明確にする（`research-workflow.md`のPhase 3参照）。

## 最重要UX指標

定量計測できるかどうかに関わらず、以下を重要概念として扱う。

| 指標 | 意味 |
|---|---|
| Time to Discovery | 興味のあるイベントを見つけるまでの時間 |
| Time to Decision | イベント参加可否を判断できるまでの時間 |
| Interaction Cost | 目的達成までに必要な、タップ・クリック・スクロール・判断の量 |
| CTA Clarity | 次に何をすればいいか分かる度合い |
| Information Completeness | 参加判断に必要な情報が揃っているか |

## イベント参加判断に重要な情報（基本優先順位）

1. イベント名
2. 開催日
3. 開催時間
4. 場所
5. 対象者
6. 内容
7. 料金
8. 予約・申込の必要性
9. 主催団体
10. 公式情報

ただしページ・文脈によって優先順位は変えてよい（一覧カードでは1〜4程度に絞り、詳細ページ・モーダルで全項目を出す、という現状の設計は妥当）。

## 実データが示す前提条件（286件の公開イベントを実測）

UI判断は以下の実態を前提にすること。詳細な調べ方は`review-checklist.md`のEdge Casesおよび下記コマンド参照。

- **最長イベント名**: 96文字（英語論文タイトルの引用込み講演）。カードでの省略・折り返し設計は必須で、「短いタイトル前提」のレイアウトは成立しない。
- **最長会場名**: 38文字（`東京大学本郷キャンパス 情報学環・福武ホール地下2階 福武ラーニングシアター`）。実際に2026-09、投稿用画像でこの会場名がカードからはみ出す不具合が起きている（`image-generator.js`の`drawWrappedInfoLine`で対処済み）。**「長い会場名」は例外ではなく実在するケース**として設計する。
- **最長主催団体名**: 32文字。
- **1日の最大イベント数**: 9件（2026-07-11）。カレンダーの日別チップは3件+「他N件」で畳む設計になっており、これはこの実データを前提にした妥当な設計。
- **複数日イベント**: 77件（うち14件が14日以上の長期開催）。月間カレンダーは短期複数日イベントを週バーで、長期開催イベントは別ウィジェットで表示する2系統設計になっている。
- **情報欠損の実態**: `location`欠損61件、`externalUrl`欠損42件、`startTime`欠損134件、`feeType`が`unknown`のもの196件（286件中）。**情報が全部揃っているイベントの方が少数派**。「全フィールドが埋まっている前提」のUIは実データの過半数で崩れる。空欄・不明表示のフォールバック設計は必須（`CLAUDE.md`の「不明」原則と地続き）。
- **`orgId`保有**: 14件のみ。ほとんどのイベントは団体ページとの自動連携がなく、`organizer`のテキスト一致で拾われている（`organizations-page.js`の`isEventRelatedToOrg`参照）。

新しいUI要素を提案するときは、このような「長い」「欠損している」「大量にある」実データで壊れないかを必ず確認する（`review-checklist.md`のEdge Cases）。

## Waseda Calendarで避けるもの

- 過剰な装飾
- 情報量を増やしただけの改善
- 不必要なモーダル
- 不必要なカルーセル
- hover前提UI（モバイルが主要な利用形態のため、`mobile-guidelines.md`参照）
- モバイルで押しづらいUI
- 過度なアニメーション（`prefers-reduced-motion`は既にグローバルで尊重済み。壊さないこと）
- CTAの乱立
- 同じ情報の重複表示
- 目的不明のアイコン
- 流行だけを理由に導入するUI
- 他サービスの安易なコピー
- デスクトップ中心設計

## 既に実装されている、良い判断の実例（再発明しないこと）

- **団体一覧の初期非表示**（`organizations-page.js`の`hasSearched`）: 504件を一気に出さず、検索・絞り込みを促す。Cognitive Loadへの対処。
- **団体カードのコンパクト化**（2026-09実施）: 説明文・リンクをカードから外し、詳細ペインに集約。Progressive Disclosure。
- **本日/今週セクションの折りたたみ**（`script.js`の`setupSectionToggle`）: 初期折りたたみでスクロール量を削減しつつ、件数バッジは畳んだ状態でも見せる。
- **複数日イベントバーの3レーン制限**（`MAX_VISIBLE_WEEK_BAR_LANES`）: カレンダーの週の高さを安定させるためのトレードオフ。ただし、レーンの優先順位は「開始列が早い順、同点はファイル内の並び順」という素朴なロジックで、長期間イベントが短期イベントに押し出されて非表示になるケースがある（既知の改善余地、後述）。
- **「今日、何する？」おすすめ機能**（`recommendation.js`）: Hick's Lawへの対処として、504件から一気に選ばせず4問の質問で3件に絞る。
- **参加申し込みリンクと公式サイトリンクの分離**（`registrationUrl`導入、2026-09-14）: Information Scentへの対処。1つの曖昧な「詳細を見る」に統合しない。

## 既知の改善余地（このSkill作成時点で未対応）

以下は今回のリポジトリ調査で見つかったが、Skill作成の範囲外として未修正のもの。UI相談を受けた際の判断材料として記録しておく。

- **複数日イベントバーのレーン優先順位**: `script.js`の週バー割り当ては「開始列が早い順、同点は`events.js`内の記載順」で決まる。10日間続く長期イベントが、たまたま同じ日に始まる複数の短期イベントに紛れて非表示レーンに追いやられ、「他N件」としてしか見えなくなるケースが実際に発生した（2026年9月第3週、関東学生バドミントン秋季リーグ戦の例）。改善するなら「開催日数が長い方を優先」のような並び替えが有力候補だが、Owner未確認のため未実装。
- **デザイントークンの一部不統一**: 件数表示（`#today-count`/`#upcoming-count`）がインラインstyleで`.section-count`クラスと重複した指定をしている（`design-system.md`参照）。
