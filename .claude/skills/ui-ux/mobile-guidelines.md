# モバイルガイドライン

Waseda Calendarはモバイルを主要な利用形態として扱う（`CLAUDE.md`にも明記済み: 「Mobile is the primary usage mode」）。PC版を縮小したものではなく、モバイルを主として設計・検証する。

## Thumb-friendly UI

頻繁に使う操作（カレンダーの月送り、フィルター開閉、モーダルを閉じる等）を親指で押しやすい位置に置く。画面の一番上・一番端は、片手操作では届きにくいことを意識する。

## Touch Target（タップ領域）

十分なタップ領域を確保する。目安は一辺44px前後（Apple HIG/Material Designの一般的な基準）。

- **既存の良い例**: `.event-external-link`は「以前はpaddingが無く行の高さそのまま(20px程度)しかなくモバイルで押しにくかった」ため、タップ領域確保の修正が入っている（`style.css`コメント参照）。新しいリンク・ボタンでも文字サイズがそのままタップ領域にならないよう、padding込みで44px前後を確保する。
- **確認ポイント**: カレンダーグリッドの日付セル・複数日イベントバーなど、小さい要素が密集する箇所は特にモバイル幅（〜390px）で実際にタップして確認する。

## Vertical Scanning（縦方向の走査）

ユーザーは縦方向に高速に情報を確認する前提で設計する。横スクロールが必要なUI（表・カレンダー等）は、モバイルでは特に避けるか、明確にスクロール可能と分かる見た目にする。

## Above the Fold（ファーストビュー）

画面上部に何を置くべきかを考える。ただし**無理にすべてをファーストビューへ詰め込まない**——本日/今週セクションの折りたたみ（初期折りたたみ）は、ファーストビューに情報を詰め込みすぎず、必要な人だけが展開する設計の実例。

## Sticky UI（固定表示）

固定UIは便利だが、コンテンツ領域を圧迫しないか必ず検討する。特にモバイルの縦幅は限られているため、ヘッダー等の固定要素が画面の大きな割合を占めていないか確認する（`--header-h: 64px`が現状の基準値）。

## Filters（フィルター）

モバイルではフィルターの情報量・高さ・操作回数に注意する。

- 現状、絞り込みパネルはPC/モバイル共通で初期折りたたみになっている（2026-09に統一済み）。
- 団体一覧の504件は初期表示せず、検索・絞り込みを促す（`organizations-page.js`の`hasSearched`）。
- 新しいフィルター項目を追加する前に、Hick's Law（`principles.md`）に照らして本当に必要か検討する。

## Calendar（月間カレンダー）

月間カレンダーはモバイルで特に難所になりやすい。以下を必ず考慮する。

- **横幅**: 7列のグリッドが狭い画面でどこまで潰れるか。日付・件数が判読できるか。
- **レーン数**: 複数日イベントバーのレーン数（現状3レーン上限、`MAX_VISIBLE_WEEK_BAR_LANES`）。モバイル幅でさらにレーンを増やすと1マスが小さくなりすぎる。
- **イベント件数**: 1日に最大9件（実データ、`waseda-calendar-ux.md`参照）というケースが実在する。「他N件」への畳み込みが正しく機能しているか。
- **長期イベント**: 14日以上の長期開催イベントは週バーから分離し、別ウィジェットで表示している（`renderLongRunningEventsWidget`）。モバイルでこのウィジェットが画面を占有しすぎないか。
- **タップ精度**: 小さい日付セル・イベントバーを指で正確にタップできるか。
- **日別詳細への移動**: セルをタップしたときに`showDayEvents()`等で日別一覧に遷移できる導線が機能しているか。

なお、モバイル幅ではカレンダーがグリッド表示ではなくリスト表示（`renderCalendarList`）に切り替わる実装が既にある。新しいカレンダーUI変更は、グリッド版・リスト版の**両方**を確認すること（`isMobileCalendarLayout()`で分岐）。

## Hover禁止

**hoverしないと情報・操作が分からない設計は禁止する。** モバイルには物理的にhover状態が存在しない。

- 新しいUI要素で「hoverで詳細が出る」「hoverでボタンが現れる」ような設計を提案しない。
- 既存コードのhover効果（`.btn-enjy:hover`等）はあくまで補助的な視覚フィードバックであり、情報そのものをhover内に隠していない点を確認する。
- ツールチップ（`title`属性）に重要情報を入れる場合、モバイルでも別の手段（タップで展開、テキストとして常時表示等）でその情報にアクセスできることを確認する。カレンダーの複数日イベントバーは`title`属性に開催期間を入れつつ、開始週のセグメントには常にテキストとしても表示する二重対応になっている（この設計を新しいツールチップ利用時も踏襲する）。

## 検証の実務

- レイアウト変更は**〜320px/375px/390px幅**で必ず確認する（`CLAUDE.md`と同一基準）。
- PCのみで確認して「完了」としない（SKILL.md禁止事項6）。
- Playwrightで自動検証する場合、モバイル幅のviewportと通常のPC幅viewportの両方でスクリーンショット・操作確認を行う（ただし変更の低リスク・高リスクに応じて検証の重さを調整する。過剰な検証はしない——`CLAUDE.md`「作業の進め方」参照）。
